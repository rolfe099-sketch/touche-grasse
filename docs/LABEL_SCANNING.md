# Reviewed nutrition-label scanning

Log → Scan → Photograph nutrition label opens the camera on the native app. Press the shutter and choose Use Photo. On the web, Scan a nutrition label opens the existing food-label form, then Choose label photo opens the file picker. Barcode scanning has its own Scan barcode action. Review the recognized values, select the appropriate column when needed, enter the product name and amount, then Confirm and add. This saves the food and appends a draft ingredient; the usual meal Log action records it as eaten. Existing label editing uses the same workflow.

## Accuracy and preparation

The parser accepts explicit per-100-g/ml headers and measured serving weights/volumes. Multiple columns remain separate and require a selection; prepared alternatives are marked and require explicit selection. Serving values are normalized using their printed g/ml amount. Amounts are cleared when switching g/ml; no density, cooking yield or absorption is inferred. Unknown serving weights require manual entry.

English and Norwegian nutrient names, decimal commas, stated kcal, stated kJ (4.184 kJ/kcal), and explicit gram/milligram/microgram units are supported. Energy is not inferred from macros. Sub-nutrients such as saturated fat and sugars do not replace fat/carbohydrates. Missing fiber stays unknown, distinct from an explicit zero. Low-confidence readings (when supplied by the engine), inequalities, suspicious numeric characters, implausible or conflicting values and unaligned column counts remain blank for correction. Browser readings use separate English and Norwegian passes; an independently clear reading can fill a missing value, while conflicting confident readings, detected bounds and ambiguous columns remain blocked. Native engines do not expose confidence through the selected module, so no confidence score is fabricated.

Separate heading/value observations are paired only across adjacent numeric/unit lines, stopping at other headings. A bare macro number without a read unit offers explicit gram confirmation rather than becoming a nutrition value automatically. Older native label drafts are reprocessed from retained text to recover newly readable values while preserving corrections. The native reader optionally retries a closer table crop when values are missing; the crop includes observed columns and does not infer missing values. Browser normalization uses lossless PNG to preserve small unit glyphs.

The photo can be enlarged inline. Every value remains editable and requires user confirmation against the package. OCR is a reading aid, not an independently verified food record. Reviewed foods retain original normalized scan nutrition, basis, recognition/review time and per-field correction attribution. Existing Open Food Facts lineage/license metadata is retained when correcting those records. Historical food, recipe and eaten-portion snapshots remain unchanged.

When a closer reading retains only kJ, the printed kcal from the other reading takes priority only if both retain identical stated kJ values. This avoids treating the exact conversion of rounded kJ as a conflicting measurement. Different stated kJ or different printed kcal remain blocked. Mixed positioned cells and paragraph observations keep their reading order. Rejected fields show their captured source text inline; conflicting passes retain both pieces of evidence for review.

A native geometric row can swallow the energy observation into its table header. If no energy row was identified geometrically, the parser can recover the explicitly labeled energy reading from the original OCR text only when its reference columns agree. It does not override a previously rejected energy reading, use macro estimates, or bypass weak browser confidence. An unambiguous macro number with a missing or corrupted short unit (for example `Protein 5,6 Dr` or `Kostfiber 3,2`) remains unknown and offers explicit gram confirmation. Incompatible known units, unclear numbers and conflicting confirmation candidates remain blocked. The UI distinguishes `Confirm unit` from a missing value and preserves the original unknown reading separately from the user-confirmed value.

Version-2 unfinished native reviews are repaired on reload where these safeguards allow it: missing energy association can be filled from the retained text, while macro candidates still require user confirmation. Existing edits and known/rejected readings remain intact. This repair changes neither saved foods nor historical entries and does not require another photo.

## Privacy, persistence and offline use

Photos are processed locally: `expo-ocr-kit` 0.1.4 uses the platform engine; the browser uses Tesseract.js 7.0.0 with self-hosted English/Norwegian models. The app sends no image to an OCR service. Source photos are not included in diary exports or recovery copies. Native normalized temporary images are released when the scan is replaced or its view closes; the system photo picker may manage its own cache. Re-encoding strips EXIF and normalizes orientation before recognition.

Label text, selected column, field corrections and the amount are retained in optional Quick Entry label drafts, independently of ordinary meal and repeat drafts. Saving the food, updating the specified meal draft and removing its label draft occur in one transaction. Discard label draft removes only that unfinished label, keeping foods and the meal draft. Failed writes keep the previous acknowledged state. Backup imports merge label drafts while keeping current drafts for matching keys. A restored review keeps text rather than its photo and asks the user to compare with the package or select the photo again.

Confirmed products work through saved-barcode lookup offline. Browser OCR assets are downloaded from the app origin on first use and cached by the production service worker; the normal app shell does not precache the approximately 25 MB of alternative engine/model assets. The current browser only fetches its supported engine variant and selected languages. After an app update or cleared cache, OCR assets may need downloading again. Dev/Metro previews do not register the production worker. Native OCR is available only in a development/native build containing the module; older binaries keep manual entry usable and explain the update requirement.

Capture is user-started. Navigation, backgrounding, replacement and cancellation invalidate pending results. A bounded timeout provides manual fallback. Native platform recognition may finish internally after cancellation, but its late result cannot apply values or add food.

## Verification and limits

Local verification on 4 November 2026: 218 unit/storage tests passed, TypeScript and ESLint passed, Chromium completed with 58 passed/2 intentional skips, and iPhone-sized WebKit completed with 26 passed/1 intentional skip. Browser tests include a real second OCR pass while offline after warming the local asset cache. The retained native-text regression recovers 488 kcal and 23 g fat from the reported split observations, with explicit gram confirmation for the bare 63. These results do not resolve the owner's latest physical-iPhone report of blank energy/fat fields; the current recognized text has been requested. See [physical acceptance](IPHONE_TESTING.md#physical-acceptance).

Domain and real storage-adapter tests cover parsing, column isolation, exact normalized nutrition, corrections, partial data, retained drafts, atomic failure, barcode duplicates and historical snapshots. Session tests exercise permission/picker races, cancellation, timeout and owned-resource cleanup through fake ports. Browser tests use actual rendered label images and the real local OCR engine, not recognition-response fixtures. They separately test manual fallback, offline reuse and reload. The current real two-column synthetic image needs manual protein/fiber correction because the OCR engine misreads small numbers/units; the test verifies those values stay unknown until corrected. The pre-existing expo-camera web adapter also requests its QR-reader script from jsDelivr on import; no label image is sent in that GET. This does not establish camera accuracy on every package or physical iPhone OCR acceptance; record those results in the iPhone test table.

Dense, curved, reflective, blurry or unusually arranged tables can require a closer photo, a crop made in the phone's photo editor, or manual correction. Paragraph-only extraction is handled conservatively. Barcode detection is still a separate existing camera action; label OCR does not infer a barcode or product name from a table. The app does not track salt, sodium or additional micronutrients in this iteration.

The Linux WebKit synthetic-image run also gives the fat row insufficient confidence, unlike the Windows run. Its test requires an explicit correction, retains the original unknown scan value and records the corrected value as user-confirmed. The confidence threshold remains unchanged; these fixtures do not establish equivalent OCR quality across platforms or physical-camera acceptance.
